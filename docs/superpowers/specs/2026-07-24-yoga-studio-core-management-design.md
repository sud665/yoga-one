# 요가원 관리 PWA — 코어(회원·강사·클래스 관리) 설계

- 작성일: 2026-07-24
- 상태: 설계 승인 완료, 사용자 최종 리뷰 대기

## 1. 배경 및 스코프

요가원 관리 시스템은 강사관리·클래스관리·회원관리·수강료관리·1:1 채팅·단체채팅까지 총 6개 기능을 필요로 한다. 이 스펙은 그중 서로 강하게 의존하는 **코어(회원관리 + 강사관리 + 클래스관리)** 만을 다룬다.

**이번 스펙 범위**
- 회원관리
- 강사관리
- 클래스관리 (반복 시간표, 세션, 예약, 정원/대기명단, 출석)

**후속 스펙으로 분리 (이번 스펙 대상 아님)**
- 수강료관리 (결제, 수강권/횟수권 유효성 검사, 청구)
- 채팅 + 단체채팅
- 전자계약 (요가원-회원 등록계약: 이용약관·환불규정 문구, 전자서명, 계약서 PDF 보관/재발급)

후속 스펙들이 코어 데이터에 자연스럽게 이어붙을 수 있도록, 아래 데이터 모델에 최소한의 확장 지점(`profiles.contract_status`, 예약/세션 테이블 구조)을 마련해 둔다.

## 2. 서비스 형태

- **멀티테넌트 SaaS**: 여러 요가원(스튜디오)이 각자 독립적으로 가입해 사용하는 제품. 요가원 단위 데이터 격리가 필수.
- **역할**: 원장(owner) · 강사(instructor) · 회원(member) 3개 역할 모두 로그인해서 사용하는 올인원 구조.
- **온보딩**: 원장이 셀프서비스로 가입하며 신규 요가원(테넌트)을 생성한다. 별도 영업/승인 절차 없음.
- **강사/회원 등록**: 원장이 초대링크(코드)를 발급하고, 상대방이 링크를 통해 가입하면 해당 요가원 소속으로 자동 연결된다.

## 3. 전체 아키텍처

- **프레임워크**: Next.js (App Router) + TypeScript
- **백엔드**: Supabase (Postgres + Auth + Realtime + Storage)
- **스타일링**: Tailwind CSS, 모바일 우선 반응형
- **PWA**: Serwist로 manifest + service worker 구성. 설치가능성 확보가 목적이며, 정적 자산만 캐싱한다. 오프라인 상태에서는 데이터 캐싱 없이 안내 화면만 표시한다 (오프라인 데이터 동기화는 범위 밖).
- **인증**: Supabase Auth — 이메일/비밀번호 + 카카오 OAuth
- **배포**: Vercel

**데이터 접근 패턴 (Supabase 네이티브 하이브리드)**
- 조회와 실시간 구독은 클라이언트에서 Supabase SDK로 직접 호출하고, Row Level Security(RLS)가 테넌트·역할별 격리를 담당한다.
- 정원 체크, 대기명단 자동 승격처럼 동시성에 민감한 쓰기 작업은 Postgres RPC 함수(단일 트랜잭션)로 서버 측에서 원자적으로 처리한다.
- 이 패턴을 선택한 이유: 개발 속도가 빠르고, 향후 채팅 스펙에서 Supabase Realtime을 그대로 재사용할 수 있다. (기각한 대안: 모든 접근을 서버 게이트웨이 뒤로 숨기는 방식은 통제는 세밀하나 개발량이 늘고 Realtime 이점을 포기하게 됨. Supabase를 DB로만 쓰는 방식은 Supabase 선택 이유 자체가 없어져 기각.)

**멀티테넌시 격리**
- 공유 스키마 + 모든 테이블의 `studio_id` 컬럼 + RLS 정책으로 격리한다. (기각한 대안: 테넌트별 스키마 분리나 프로젝트 분리는 요가원 수가 늘어날수록 운영 부담이 커져 Supabase SaaS 구조에 맞지 않음.)

## 4. 테넌트 · 인증 · 초대 모델

- **`studios`**: 요가원(테넌트) 마스터. 원장 셀프가입 시 1건 생성.
- **`profiles`**: Supabase Auth 유저와 1:1 매핑 (`id = auth.uid()`). `studio_id`(FK), `role`(owner/instructor/member), 이름, 연락처, `contract_status`(not_required/pending/signed — 전자계약 스펙을 위한 확장 필드) 포함.
- **`invites`**: `studio_id, role, code, expires_at, used_at`. 원장이 강사용 또는 회원용 초대링크·코드를 발급한다.
- **가입 흐름**
  1. 원장: 이메일 또는 카카오로 가입 → `studios` 1건 + `profiles`(role=owner) 자동 생성 → 대시보드 진입.
  2. 강사/회원: 원장이 발급한 초대링크 클릭 → 이메일 또는 카카오로 로그인 → 초대의 `studio_id`·`role`로 `profiles` 생성. 회원인 경우 `contract_status=pending`으로 시작.
  3. 초대 코드 없이 임의로 가입하는 경로는 없다 (반드시 유효한 초대를 경유).
- **RLS 원칙**: 모든 조회·쓰기는 `profiles.studio_id`가 요청자 본인의 것과 일치할 때만 허용한다. 강사는 자신이 담당하는 세션만, 회원은 자신의 예약만 쓰기 가능하도록 역할별 정책을 분리한다.

## 5. 데이터 모델 (클래스 · 예약)

- **`class_templates`**: 반복 시간표 원본. `studio_id, title, instructor_id, day_of_week, start_time, duration_min, capacity`
- **`class_sessions`**: 템플릿에서 자동 생성되는 개별 회차. `template_id, studio_id, date, instructor_id`(당일 대타 등 override 가능), `capacity`(override 가능), `status`(scheduled/cancelled)
  - 세션 생성 정책: 템플릿을 등록·수정하는 시점에 향후 8주치를 미리 생성하고, 이후 매주 배치로 다음 1주를 채워 넣는 롤링 윈도우 방식.
  - `instructor_id`는 `role`이 `instructor`인 프로필뿐 아니라 `owner`인 프로필도 참조할 수 있다 (원장이 직접 수업을 진행하는 소규모 요가원을 지원하기 위함).
- **`bookings`**: `session_id, member_id, status`(booked/waitlisted/cancelled/attended/no_show), `created_at`
  - **예약 RPC**: 세션 정원과 현재 `booked` 상태 수를 같은 트랜잭션 안에서 비교한다. 여유가 있으면 `booked`, 없으면 `waitlisted`(대기 순번은 `created_at` 오름차순)로 기록한다.
  - **취소 RPC**: 본인 예약을 `cancelled`로 변경하고, 같은 트랜잭션에서 해당 세션의 가장 오래된 `waitlisted` 1건을 `booked`로 자동 승격한다. v1에서는 취소 마감 시간(cutoff)을 두지 않는다 — 세션 시작 전까지 언제든 취소 가능하다.
  - **출석 처리**: 강사가 세션 종료 후 각 예약 건을 `attended` 또는 `no_show`로 표시한다.
  - 대기명단에서 예약으로 자동 승격되어도 v1에는 별도 알림(푸시/문자)이 없다. 회원은 본인 예약 목록 화면에서 상태 변경을 확인해야 한다. 실시간 알림은 후속 채팅 스펙에서 다룬다.
  - v1에서는 수강권(횟수권/기간권) 유효성 검사를 하지 않는다. 회원이면 누구나 자유롭게 예약할 수 있다. 수강권 검증은 후속 수강료관리 스펙에서 이 예약 플로우에 훅을 추가하는 방식으로 확장한다.

## 6. 핵심 플로우 · 역할별 화면

**플로우**
1. 원장 온보딩 → `studios` + `profiles`(owner) 생성 → 대시보드 진입
2. 원장이 강사·회원 초대링크 발급 → 상대방 가입 → `profiles` 생성
3. 원장이 `class_templates` 등록 → 세션 자동 생성 (8주 롤링)
4. 회원이 세션 조회 → 예약(정원 체크 RPC) → 필요시 취소(대기자 자동 승격 RPC)
5. 강사가 담당 세션 종료 후 출석 체크 (attended/no_show)
6. 원장은 대시보드에서 강사·회원 CRUD, 전체 시간표, 예약/대기 현황을 확인

**역할별 라우트**
- `/admin/*` — 원장: 대시보드, 강사관리, 회원관리, 시간표관리, 예약현황
- `/instructor/*` — 강사: 내 수업 목록, 세션별 출석체크
- `/member/*` — 회원: 시간표 조회, 예약/취소, 내 예약 목록
- 로그인 후 `profiles.role` 값에 따라 자동으로 해당 라우트로 이동한다.

## 7. 에러 처리

- **동시 예약 경쟁**: 정원 마감 직전 여러 명이 동시에 예약을 시도하면 RPC 트랜잭션이 순서대로 처리하고, 마감 이후 요청은 자동으로 `waitlisted`로 전환하며 "정원이 마감되어 대기명단에 등록되었습니다"를 안내한다.
- **초대 코드 문제**: 만료되었거나 이미 사용된 코드는 명확한 에러 화면과 함께 원장에게 재발급을 요청하라는 안내를 표시한다.
- **권한 위반(RLS)**: 다른 요가원(studio) 데이터에 접근하려는 시도는 403으로 처리하고 공통 에러 페이지로 유도한다.
- **오프라인 상태**: 네트워크 끊김을 감지하면 배너로 안내한다. 예약 등 쓰기 작업은 오프라인 상태에서 실패 처리 후 재시도를 유도한다 (오프라인 큐잉은 범위 밖).
- **카카오 로그인 실패/취소**: 이메일 로그인으로 전환하도록 안내한다.

## 8. 테스트 전략

- **RPC 단위 테스트**: 예약·취소·대기명단 자동 승격 로직. 특히 정원 1자리에 동시 요청이 몰리는 동시성 시나리오를 반드시 포함한다.
- **RLS 정책 테스트**: 다른 studio 데이터 접근이 실제로 차단되는지 검증한다 (테넌트 격리).
- **역할별 접근 테스트**: 강사가 다른 강사의 세션을 수정할 수 없는지, 회원이 다른 회원의 예약을 볼 수 없는지 검증한다.
- **E2E 시나리오**: 원장 온보딩 → 초대 발급 → 강사/회원 가입 → 시간표 등록 → 회원 예약 → 정원 마감 → 대기명단 등록 → 취소 → 자동 승격 → 출석 체크까지 전체 흐름을 한 번에 검증한다.

## 9. 후속 스펙 메모

- **수강료관리**: 결제/청구, 수강권(횟수권/기간권) 발급과 잔여 횟수 관리, 예약 시 수강권 유효성 검사 훅 추가.
- **채팅 + 단체채팅**: Supabase Realtime을 그대로 활용해 1:1/단체 메시징 구현.
- **전자계약**: `profiles.contract_status`를 실제로 채우는 계약서 템플릿(이용약관·환불규정 문구) 관리, 전자서명 캡처, 서명본 PDF 생성·보관·재발급.
